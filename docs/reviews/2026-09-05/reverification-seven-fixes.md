## 原始失败与验证边界

首次 Maven/Redis 验证的源代码归档使用了 1970 时间戳，Maven 未复制非过滤 SQL 资源而导致 Spring 启动失败。已修正测试归档、在新隔离目录重跑并通过，未为此改动产品代码。部署测试初次启动的目录权限/换行问题也属于测试夹具，已保留原日志并纠正；宿主机账号、sudoers 和现有服务未改动。

上轮整组信号测试的 20 秒超时，本轮再次复现并捕获现场：普通退出场景 `container-query-partial-7` 中，父 Bash 已在 cleanup 内等待，而刚 fork 的 `sleep 60` 子进程仍存活。代码与进程状态指向子进程尚在初始化时收到 TERM 的启动竞态。同步稳定了这处测试夹具：真实子进程完成 TERM 默认行为初始化后写入就绪文件，父进程有界等待就绪，再执行原有退出/信号场景。增加失败 case 输出，保持实际 cleanup、20 秒断言、122 个状态场景及 canary 检查不变；修后独立和完整组合回归均通过。

本轮没有运行浏览器或线上 GitHub Actions，也没有执行完整 Docker 安装/迁移部署 E2E。Docker 查询失败回归控制外部命令边界，PostgreSQL/Redis 使用真实服务，不能把这些证据混称为完整部署验收。前端保留既有的大分块提示。各测试临时容器已清理，证据文件留在独立目录。
